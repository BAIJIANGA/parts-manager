# 元器件物料管理系统

一个**本地原生窗口**的元器件库存 / 出入库 / 项目 BOM 管理程序。
专为「Altium Designer + 立创商城(LCSC)」的工作流设计:**商品编号(C-号)是元件的天然主键**。

**零第三方依赖** —— 只用 Python 标准库(含 tkinter),不需要 pip、不需要 Node、
不需要数据库服务、**不开端口、不连网络**。

---

## 快速开始

双击 `dist\元器件物料管理\元器件物料管理.exe` 即可。

**不需要装 Python,不需要装任何东西,不弹命令行窗口,也不打开浏览器。**
整个文件夹拷到 U 盘或别的电脑照样能跑 —— 因为内嵌了 Python 运行时(`runtime\`)。

界面是原生 Tkinter 窗口,七个标签页:总览 / 库存 / 出入库 / 项目 BOM / 采购 / 仓位 / 流水。
关掉窗口进程就退出,不残留后台。

> 程序**完全不碰网络**:没有任何监听端口,没有 HTTP 服务,不需要防火墙规则。

### 桌面版是怎么复用后端逻辑的

`app/gui.py` **不重写任何业务逻辑**,而是直接调用 `app/server.py` 里的路由处理函数。
能这么做的原因:`route` 装饰器原样返回函数,而 `Ctx` 只读 `query / body / upload / con`,
完全不依赖 HTTP。

```python
ctx = server.Ctx(None, con, {"state": "out"}, {}, None)   # 合成一个请求上下文
status, payload = server.list_components(ctx, None)       # 直接当普通函数调用
```

所以桌面版和(仍然保留的)网页版**语义逐字一致**,不存在两套实现慢慢走偏的问题。

## 功能

页签从左到右就是一条使用动线:
**总览 → 库存 → 出入库 → 项目 BOM → 采购 → 仓位 → 流水**
(先看全局 → 再看我有什么 → 动库存 → 看待做的项目 → 看要买什么 → 东西放哪 → 查账)。

### 0. 先弄懂这 6 个词

整套系统就靠这 6 个数字说话。后端把它们收敛成几段共用的 SQL 片段
(`ON_HAND_SQL` / `REQUIRED_SQL` / `ON_ORDER_SQL` 拼进 `COMPONENT_SELECT`),
所有页面都从同一处取数,不会出现「这一页说缺、那一页说不缺」:

| 词 | 算法 | 含义 |
|---|---|---|
| **现有** `on_hand` | `SUM(stock.qty)` | 手上真正有多少 |
| **安全** `min_stock` | `component.min_stock` | 希望至少留多少 |
| **需求** `required` | `SUM(bom.required_qty × MAX(project.qty, 1))` | 在做的项目要吃掉多少 |
| **缺口** `deficit` | `max(0, 需求 − 现有)` | 还差多少 |
| **在途** `on_order` | `SUM(purchase.qty − purchase.received)`,只算 `status='ordered'` | 已下单、还没到货 |
| **该买** `to_order` | `max(0, 目标 − 现有 − 在途)`,其中 目标 `= max(需求, 安全)` | 建议补多少 |

> **这里刻意偏离了 InvenTree。** InvenTree 的 `quantity_to_order()` 是
> `required -= max(total_stock, minimum_stock)`:需求 50 / 安全 100 / 现有 30 会
> 算成 `50 − max(30, 100) = −50 → 0` —— 明明已经跌破安全库存,却建议不买。
> 本项目的目标是「把需求和完全库存都填满」,同一场景给出 **70**;
> 需求 200 / 安全 100 / 现有 30 时 InvenTree 给 100,本项目给 **170**。
> 差异只在那个 `max` 摆在哪一侧。

**在途把「想买」排除在外**:`purchase.status` 只有 `ordered` 才算。
否则一个还没下单的念头就能把「该买」压成 0,东西永远买不回来。

### 0.1 设计取向(以及为什么)

做这套东西之前把同类开源项目(以及它们怎么死的)翻了一遍,有 4 条结论直接决定了
现在的形态:

1. **这个品类的头号死因是「弃用」,不是「功能少」。** GitHub 上 `electronic component
   inventory` 只有 122 个仓库,绝大多数个位数 star、作者单打独斗、好几年没动;
   曾经的事实标准 PartKeepr 已经归档(官网域名都被抢注成了赌场广告页)。
   所以衡量标准不是功能多少,而是**碰一个料要付多少维护成本**。
2. **数据录入是弃用的头号原因。** 社区里最扎人的一句是「你成了它的奴隶」——
   每用一次料都要去改一次数据库,人就不改了,数据一烂整套系统就废了。
   对策:**录入必须发生在刚拆快递、袋子还在手上那十几秒**,而且能省一步就省一步。
   所以有了两条录入路径:
   - **⚡ 快速入库(Ctrl+I)** —— 单个料。只问「是什么 / 几个 / 放哪」,搜得到回车入库,
     **搜不到就当场新建一条最小记录**(只填名称、归到「未分类」),绝不拦着你先记下来;
     入库后窗口不关,可以连着录下一袋。
   - **📋 批量入库(Ctrl+B)** —— 一整箱货 / 对着采购单。粘贴、预览、确认,一次落库。
     对不上的行会明确标出来而不是猜。

   配套地,`stock_move` 不写仓位时自动落到这个元件的 `default_loc_id`
   (没设就进「未分类」)—— 常用的料设一次「固定的家」,以后就不该再问。
3. **搜索比分类学有用。** 「YAGNI:搜索往往比建立、执行和维护一套分类体系更高效」。
   所以分类始终是**可选**的:`component.category` 有默认值,新建时只强制填名称;
   而搜索是主入口,前端有搜索框、`Ctrl+I` 也是先搜。搜索命中
   名称 / 商品编号 / 厂家料号 / 厂家 / 值 / 封装 / **丝印** / **参数JSON** / 备注 / 品类。
4. **数量要能"粗着记"。** 没人愿意数电阻,但每个人都想知道"我到底有没有 0805 的
   某个阻值"。所以既有精确数量,也有 `min_stock` 安全库存和
   充足/缺料/缺货 这套粗粒度状态 —— 两条路都留着,不强迫你走哪条。
5. **录得快,就必须退得掉。** 第 2 条把录入成本压到最低,代价是**录错也变容易了**
   (多按一个 0、选错仓位)。如果不给退路,用户会用「干脆不记」来规避风险 ——
   等于把第 2 条的好处全抵消掉。所以有 **Ctrl+Z 撤销**,而且撤销是
   **补一笔反向流水**,不是删记录:账本仍然能按流水重建,也查得出是谁改的。
   这是「让账本可追溯」和「让用户敢用」之间必须同时成立的两件事。
6. **重复料是必然会发生的,所以得有个地方收拾它。** BOM 要反复导入,而不同时期的
   BOM 里同一个料可能一条带料号、一条只有值+封装 —— 于是库里长出两三条,库存还分散
   记着。这类数据腐烂不会自己好,只会越来越难收拾。所以 `🔍 查重与合并` 按
   **从硬到软**三档找可疑重复(料号相同 / 名称相同 / 值+封装相同),并明确告诉用户
   第三档只是可疑、要他自己确认。合并时被并掉的那条**不删**,只标 `merged_into`:
   删了的话它名下的流水会被外键级联一起带走,而那是真实发生过的收发货。

顺带落进数据模型的两件事:

- **`marking`(丝印 / 顶标)是可搜索字段,而且在库存表里单独占一列。**
  拆下来的小芯片,封装上印的三个字母根本不是料号(SOT-23-5 上印 `CX4R` 的其实是
  SN74LVC1GX04),「这是什么芯片」是社区里最高频的求助。查不到就等于没存,
  所以它必须能搜、而且一眼能看到。
- **值同时存两份**:`value` 存人看的文本(`10kΩ`),`value_num` / `value_unit` 存
  解析出的数值和单位。**存数值、显示工程记号** —— 这样 `100kΩ` 才能排在 `10kΩ`
  后面,而不是按字符串排。这是无源件建模里最要紧的一个决定。
- **光能排序还不够,还得能按区间找。** 无源件的真实问法是「我这个 0805 的抽屉里
  到底有没有 1k~10k 的」,不是「把电阻按值排个序」。所以二级页有值区间 + 单位 + 封装
  的筛选栏,比的是 `value_num`。这是唯一一件「调研里点名、而通用库存系统普遍没做好」
  的事 —— 它们把值当自由文本,于是区间查询无从谈起。

### 1. 总览

一屏回答「我有什么 / 要做什么 / 要买什么」:8 个统计数字(元件种类、库存总数、
库存估值、该买种类、该买金额、在途数量、缺货种类、低于安全库存),
下面接着项目进度表和最近流水。是启动后的落地页。

### 2. 库存

首页是**一张张「大类卡片」**(电阻 / 电容 / 电感 / 发光二极管 / 芯片 IC / 连接器 …),
点卡片进入**独立的二级页面**看那个大类的具体型号,左上角「← 返回」回卡片首页。
一行摆几张卡片按窗口宽度算,窗口拉宽就多摆几张。卡片有悬停高亮。

- **首页卡片就是库里真有的品类,名单不再写死**(#32)。新库开箱时按标准名单
  (`db.category_seed()`,16 个)建**一次**品类行,所以开箱就有一套大类可挑;
  此后**再也不自动创建任何品类行** —— 卡片从品类表读,库里没有的那一档就不画
  (用户没建过「传感器」,首页就没有「传感器」这张点不动的空卡片),
  自定义品类和「未分类」也在同一份名单里。
- **「未分类」是算出来的,不是固定的品类**。只有库里**真的有没有品类的料**时,
  首页才出现这张卡片(点进去能看到那些料,方便重新归类);一件都没有它就不出现。
  它本身也删得掉;删完若还有没归类的料,它只是换个身份再出现(见下面「品类树」)。
- **删掉的大类不会自己长回来**。以前删了又回来、像是删不掉 —— 根因不是删除逻辑,
  而是**后端每次启动都在按标准名单把缺的品类行播种回来**(连 `delete_category`
  结尾那次对账也会再播一次)。现在播种只认「**这一次才把 `category` 表建出来**」
  这个时机(SQLite 自己维护的事实),老库从此完全交给用户:删掉的那一行不会在
  任何一次启动、任何一次刷新里长回来。
- **二级页面只列有库存的元件**。库存为 0 的在这一页不出现,所以点进一个还没入过货的
  大类就是空的(给一句「暂无库存元件」)。因为导入 BOM 只是记下「这块板子要用到什么」,
  东西还没买回来 —— 那属于「要买什么」,不是「已经有什么」。过滤在 SQL 层做
  (`/api/components?stocked=1`),不是全取回来再筛。
- 卡片上除了名称,还有一个**字母标识**(R / C / L / LED / IC …,沿用画图时的位号习惯)
  和一句状态:`点开查看 →`,或者 `暂无库存` —— 后者连标识一起变灰。
- **项目不在这一页**。项目 BOM 回答的是「这批料是给谁配的」,和「我有什么」是两本账,
  混在一棵树里只会让人分不清 —— 项目视角在「项目 BOM」页里单独看。
- 二级页面是平表(不是树,没有展开三角),14 列,横过来就是那 6 个词:
  **名称 / 商品编号 / 厂家料号 / 丝印 / 封装 / 值 / 现有 / 安全 / 需求 / 缺口 /
  在途 / 该买 / 状态 / 备注**。数值为 0 的格子留空,只让非零值显眼。
- **⚡ 快速入库(Ctrl+I)** 就在这一页右上角,也是收货时最该点的按钮,详见上面「设计取向」
- **📋 批量入库(Ctrl+B)**:一整箱货 / 对着采购单,一次录进去。
  一行一个料,数量写成 `x50`;直接从表格复制粘贴也行(有制表符时最后一列数字当数量)。
  故意**不把行尾裸数字当数量** —— 那样「100nF 0805」会被读成数量 805。
  点「解析预览」后每行都会对到库里的一条元件上给你看:精确命中(绿)/ 库里没有、
  会新建(绿)/ **对上了多项,需要你指定**(黄,默认跳过)。确认后才落库。
  批量操作最怕「猜错了还悄悄记进去」,所以宁可多停一步。
- **筛选栏**回答的是「我这个大类里到底有没有某一档的东西」:值 ≥ / 值 ≤ / 单位 / 封装。
  值可以写 `1k`、`10kΩ`、`0.1uF`,也认纯数字。比的是解析出来的数值(`value_num`),
  不是字符串 —— 按字符串比的话 `100k` 会被当成比 `10k` 小,区间就全错了。
  封装和单位的下拉是**分面**:只列当前范围里真有的,而且按「范围」算不是按「结果」算,
  所以选定一个封装之后别的封装不会从下拉里消失。封装按**尺寸**归并
  (`0805` / `C0805` / `SMD0805` 合一项),见下面「封装索引」。
- **🔍 查重与合并**,在「工具」菜单和这一页右上角。专治反复导入 BOM 长出来的重复料
  (见下面「设计取向」)。
- 搜索:首页搜索框回车或点「搜索」,结果也在同样的二级页面里显示。
  搜索命中 名称 / 商品编号 / 厂家料号 / 厂家 / 值 / 封装 / **封装尺寸** / **丝印** /
  **参数** / 备注 / 品类(搜 `1005` 也能把写 `0402` 的那批带出来)
- 库存状态自动标记:**充足 / 缺料(库存少于或正好等于安全库存)/ 缺货**,缺货行整行标红
- 选中任意元件看详情:仓位分布 + 最近 50 条流水
- 右键元件可直接开单(入库 / 出库 / 盘点 / 移库);双击一行是编辑
- **表格上方的行调色盘**(#28 / #34):选中一行或多行,点表格正上方那排色块 ——
  「字体颜色」和「填充颜色」各一个按钮(按钮自身显示当前选中行的颜色),点开是
  一格一格的常用色,末尾「更多颜色…」才走系统调色板(标准库
  `tkinter.colorchooser`,不引第三方库);「清除配色」回到内置规则色。
  右键菜单里也有同样三条(「文字颜色…」/「背景色…」/「清除自定义行配色」),
  和工具条走**同一条上色路径**,行为完全一致。设完重开软件还在(存在
  `ui_columns.json` 里,键是**元件 id** —— 换页面、换筛选,同一颗料还是同一个
  颜色)。
- 上完色会**取消这几行的选中**:ttk 的选中态蓝色高亮会把整行自定义色整个盖住
  (像素实测:选中时自定义色 0 像素 / 高亮蓝 12939 像素;不选中时 12841 / 0)。
  不取消就等于「点了没反应」,所以认这个取舍 —— 想接着设另一种颜色(先设字色
  再设填充)得重新选一次。
- 配色和业务规则色**不打架**:**用户明确设过的以用户为准**,没设过的沿用原来的
  规则色(缺货红底 / 缺料黄底)。所以「只设了文字色」的行背景照旧是黄底;
  一旦设了背景色,规则色就让位 —— 两个 tag 抢同一个选项只会时红时黄。

> **上色只能整行,连整列都做不到。** `ttk.Treeview` 的 `tag` 是**整行**的;而
> `column` **没有任何配色项** —— `tree.column(c, background=…)` 直接
> `TclError: unknown option "-background"`(`column` 只管宽度、对齐这些;旧文档
> 里「column 是整列的」那句是错的)。单元格级更是没有:`item()` 只认
> `image / open / tags / text / values`。要真做到 Excel 那样选中一格刷一格,
> 只能自己用 Canvas 画一张假表 —— 那是把整个列表重写一遍,为一个配色功能不值当。
> 所以这个功能的形态就是**按行**刷色,界面上也写明了「ttk 表格只能整行配色,
> 刷不了单个单元格」,不假装能一格一格刷。

> 卡片尺寸是写死的常量(`CARD_W` / `CARD_H`),子控件是用 `pack` 摆的,所以卡片上
> 必须调 **`pack_propagate(False)`** 而不是 `grid_propagate(False)` —— 前者没关的话
> 卡片会被内容撑成 130×72,和设定的尺寸对不上。`build/check_layout.py` 里有一条
> 断言专门看住这件事。

#### 2.1 菜单是四级的,而且级数由你定

库存首页那张卡片是**第一级**。点进去之后:

```
大类(卡片) → 子类(卡片,可以有好几级) → 封装(一行可点的按钮) → 具体元件(表)
```

- 给一个大多类加过子类(比如 电容 → 无极性陶瓷电容),点进去先让你选子类,
  选完才看料;子类还能再往下加,想加几级就加几级。
- **没加过子类的大类会跳过这一级**,不会让你点一个只有一项的页面。
- 封装做成一行可点的按钮而不是又一页:同一个大类里封装通常只有两三种,
  为它单开一页会把「看一眼料」变成三次点击。
- 那几个封装按钮**按尺寸归并**:`C0805` / `0805` / `SMD0805` 物理上是同一颗,
  只出一个写着 `0805` 的按钮。以前三种写法摆成三个按钮,点哪一个都只筛出
  一部分,看着像漏了数据(见下面「封装索引」)。
- **每一级都能就地改**:在卡片上点右键 → 加子品类 / 改名 / 删除,只动这一级。
  首页和中间页的顶栏还各有一个「＋ …」按钮,点一下就能加。
  「🗂 品类管理」留着看整棵树,不必为了加一个子类先打开它。
- **库里还没有这一级时,右键也要有反应**(#29,当时的方案)。那时首页那 16 个
  标准大类还是写死的名单,用户可能从没建过对应的品类行,于是这种卡片右键会静默
  什么也不做(`_menu_node` 找不到节点就 `return`)—— 用户看到的就是「点了没反应」。
  当时的绕法是:`_menu_node()` 给这种卡片**造一个虚拟节点**(`id=None`)交回调用方;
  「＋ 在这下面加子品类」**先问名字再按需把这一级建出来**;「改名…/删除…」置灰并
  写明「库里还没有这一级」(对不存在的东西「删成功」是骗人);菜单里再加一条
  「＋ 把「传感器」这一级建出来…」;并且把所有「找不到节点就静默返回」的地方都
  补上状态栏提示。
- **那套防御在第十一批整个拆了**(#32)。当时以为是「名单写死 + 用户没建过」,
  查下去才发现真正的根因在**后端**:每次启动都按标准名单把缺的品类行播回来,
  `delete_category` 结尾也顺手播一次 —— 所以删了又出现、卡片对不上树上的行。
  现在品类是**完全数据驱动**的:卡片只列库里真有的品类,不存在「库里还没有这一级」,
  也就不需要虚拟节点 / 按需建 / 置灰 / 恢复入口。**「找不到节点不许静默返回」这条
  留着** —— 别处刚删掉这一级时,状态栏至少要说一句话。
- 顶上一直有一条**面包屑**(`全部库存 › 电容 › 无极性陶瓷电容 › 0603`),
  点其中任意一级就退回那一级。
- 钻到第三级之后刷新(比如刚入完库),**还留在原来那一级**,不会被弹回首页;
  正在看的那一级被删掉了,则退到最近一个还存在的层级,不会给你一个空页。

这套菜单完全由品类表驱动,所以改菜单 = 改品类,见下面的「品类树」。

#### 2.2 属性:耐压、精度、功率、饱和电流…你自己定义

同样是 100nF 0603,一个是 50V 一个是 100V;同样是 10k 0603,一个是 1% 一个是 5%。
这类区别决定它能不能用在你那块板上,所以必须能记下来 —— 但**不能由程序预先规定**
要记哪些:光耦要「隔离电压」,电感要「饱和电流」,传感器要「量程」,
写死一份清单必然漏。

元件编辑窗口里的「属性」是一张「名称 / 值」的小表,一行一个。名称是下拉框,
按**当前品类**给出常见候选(电容给 耐压/精度/温度系数/介质…,电感给
额定电流/饱和电流…),但它**只是建议 —— 直接打字填任何名字**都行。

填完之后,这四个地方看得到:
- **收料清单**和**出库分配**各多了一列「参数」,把属性合起来显示
  (`50V · ±5%`),顺序按重要程度排而不是按字母,所以你一眼先看到耐压和精度。
- BOM 明细右边那块详情面板有一行「属性」,写全名(`耐压=50V    精度=±5%`)。
- 元件编辑窗口里的「属性」小表 —— 也就是填它的地方。
- 搜索能搜到属性值 —— 打 `50V` 就能把料筛出来。

库存列表那张表**故意没有**这一列:它已经有 14 列,实测合计 1309px、
可用 1311px,只剩 2px;再加一列必然挤爆(而且 ttk 对带 stretch 的列
不会可靠收缩,只能靠手工配平)。所以属性放在上面那四处,不硬塞进列表。

存储上用 `component.params` 一个 TEXT 列存 JSON,所以**加新属性永远不用改表结构**,
也不用版本升级。值留空和删掉这一行是两回事:留空 = 「这颗料的耐压我还没查到」,
删掉 = 「这颗料没有耐压这个说法」。

#### 2.3 品类树:菜单的骨架

品类以前只是元件上的一行文字,想改个名字得批量改元件、改一半失败就一半新一半旧,
也没法先搭好架子再往里放东西。现在它是一张真正的表(`category`)。
日常维护**不必开窗口**:在库存菜单的卡片上点右键就能加子品类 / 改名 / 删除,
只动这一级;「🗂 品类管理」用来看整棵树(哪一支在哪儿、各有多少料)。

删品类**只删这一个节点,下游一件都不丢**:

- 它的下级**接到上一级**去(删的是顶层大类,下级就各自成为顶层)
- 直接挂在它下面的元件挪到上一级;删的若是顶层大类,它没有上一级可去,
  这些元件就变成**「没有品类」**(`category_id` 置 NULL、`category` 文本清空)——
  首页那张算出来的「未分类」卡片会把它们收着,可以在那里重新归类
- 下级和上一级已有的节点**撞名就并进去**(下级的下级、元件一起挪),而不是
  甩一句「已经有同名品类了」让用户自己去改名 —— 他要的只是把这一层拿掉
- 确认框里写明「子类会接到上一级,一个都不会删」「元件会被挪走,不会被删除」

要的是整理货架,不是连货一起扔 —— 真要把某些元件也清掉,
去元件列表里一条条删,那才是明确的意思表示。

删**顶层大类**以前还要多一步「把名字记进 `hidden_cats`」(`ui_columns.json`),
因为卡片名单是写死的 `CATEGORY_ORDER`,不记就画回来。**这套机制在第十一批
(#32)整个删掉了**:首页卡片从品类表读,删掉的行本来就不会再被画出来,
不需要已删名单,也不需要「↩ 恢复删掉过的标准大类…」那条路。想再要这一档,
用「＋ 顶级品类」建一个同名的就行 —— 那是一次真实的创建,不叫「恢复」。

表结构上有一个容易踩的坑:SQLite 的 `UNIQUE(parent_id, name)` 对 NULL 是**不生效**的
(NULL 互不相等),所以顶层重名得靠一个部分索引
(`CREATE UNIQUE INDEX ... WHERE parent_id IS NULL`) 才拦得住。

另一个是**文本列和 id 列的一致性**:`component.category` 存**顶层祖先的名字**,
`component.category_id` 存树上具体那个节点。这样做的原因是:全程序里
「按品类分组 / 筛选 / 显示」的 SQL 读的都是那个文本列,让它继续只认顶层,
这些 SQL **一行都不用改**;而菜单和归属用 id,才分得清「挂在子类下」和
「直接挂在顶层」。代价是两者必须**一起写**,绝不允许出现
「文本说电容、id 指着电阻」这种自相矛盾的状态 —— 所以 `create_component` /
`update_component` 里都是成对写、`meta` 里也总是成对给。

#### 2.4 封装索引:C0805 / R0603 / L0402 认得出来

立创导出写 `C0805`,手写常常就是 `0805`,公制又是 `1005` —— 三样东西物理上是
同一个尺寸。以前程序把它们当三个不同的封装:身份键算三个,菜单摆三个按钮,
按 `0805` 筛只筛出一部分,搜 `1005` 一颗都搜不到。

现在多了一列索引 `component.package_key`,存的是**标准化之后的尺寸**
(`app/footprint.py`)。认得出的写法是
`0201 / 0402 / 0603 / 0805 / 1206 / 1210 / 1812 / 2010 / 2512`;
公制按对照表折过去(`1005`→`0402`、`1608`→`0603`、`2012`→`0805`、`3216`→`1206`、
`3225`→`1210`、`4532`→`1812`、`5025`→`2010`、`6432`→`2512`);带前缀后缀的也挖得出来
(`CAPC0805`、`CAP-0805`、`SMD0805`、`0805_1.6x0.8`)。

**公制的 0603 / 0402 故意不折算**:那会和英制的 `0603` / `0402` 撞名,
折过去反而把两种完全不同的尺寸并成一个 —— 这种错比不认更糟。

用户存进去的字**一个都不改**(`component.package` 原样保留,列表里显示的就是
他写的那个),只在**匹配、归并、搜索**这三件事上按尺寸认:

- 身份键用归一化后的尺寸,所以 `C0805` 和 `0805` 是同一个料,不会长出重复行
- 封装按钮和下拉按尺寸归并,筛选走 `package_key` 索引(料多的时候快得多)
- 搜索 `1005` 也能把写 `0402` 的那批带出来
- 出库分配的候选里,封装和这条需求一致的会标蓝并排在前面 ——
  发错货十有八九就发生在「值一样、封装不一样」的那两颗之间
- 品类推断也跟着沾光:封装写成 `CAPC0805` 这种能认出是电容(弱证据)

索引列在写入时由后端维护(建 / 改元件都会重算),老库启动时自动回填一次
(`db.backfill_package_key`),不用你做任何事;`schema_version` 因此提到 **5**。

### 3. 出入库

**这一页只查账,不开单。** 拆成 **【入库流水】/【出库流水】** 两张只读表。

为什么这么定:「出入库」这个词本身有两种读法 —— 一种读法是「一次出入库**动作**」,
另一种是「出入库**记录**」。要做的是后者:**账本**。它回答的问题是
「什么时候进了什么、什么时候出了什么」,而这个问题任何时候都问得出来。

而真正的收料/发料动作天生属于某个项目 —— 决定「这颗料该不该收、该收几个」
要看的是那张 BOM 缺什么。所以操作搬进了「项目 BOM」页(见下一节),
在那里 BOM 明细和收发货就在同一个项目的同一屏上。

- **盘点 / 移库只出现在「流水」页** —— 它们既不是进也不是出。硬塞进这两张表里,
  要么得给它们编一个方向,要么就得在一张「入库流水」里混进不是入库的东西。
- **项目下拉只列真的有该方向记录的项目**(`list_projects` 的 `moves_in` / `moves_out`)。
  导入 BOM 会建出一堆一次库都没动过的项目,全列进来的话每挑一个都是一张空表 ——
  那才是这一页真正的噪音来源。下拉里藏起来的数量会写在摘要行里。
  - 这么藏**不会**造成死路:第一单在「项目 BOM」页里开,那边列的是**全部**项目。
    (这一点和上一版不同 —— 上一版把项目卡片藏起来就真的没法开第一单了。)
- 已撤销的行**淡显但不隐藏**,「动作」列会写成 `入库(已撤销)` / `入库·撤销`。
  后一种必须能分辨:撤销一笔出库补的是**入库**,所以「入库流水」里混着反向流水。
- 选中一行可以**单独撤销**(反查回采购单也会一起退回去,见「流水」一节)。

四种动作全部**事务化**并留痕。它们的「数量」意思不一样,这是最容易记错的地方:

| 动作 | 含义 | 数量填什么 | 在哪做 |
|---|---|---|---|
| **入库 IN** | 增加库存 | 入库数量 | 项目 BOM → 元件入库 |
| **出库 OUT** | 减少库存 | 出库数量 | 项目 BOM → 元件出库 |
| **盘点 ADJUST** | 修正为实际清点值 | **实际数到的数量** | 库存页右键 / 仓位页的盘点 |
| **移库 TRANSFER** | 仓位间移动 | 移动数量 | 库存页右键 |

不挂项目的日常补货、领用:走「工具 → ⚡ 快速入库 (Ctrl+I)」「📋 批量入库 (Ctrl+B)」,
或者在「库存」页右键一个元件。**这些不进项目,但一样进流水**,所以在「不指定项目」
那一格里查得到。

- 禁止负库存(超量出库会被拒绝并提示当前数量)
- 往**标了「只用来分层」的仓位**直接入库会被拒绝并提示放到子仓位
  (见下面「仓位」)

### 4. 项目 BOM

右半边分三个子页签:**BOM 明细 / 元件入库 / 元件出库**。

- **BOM 明细** —— 这张板要用什么、还缺多少、能造几块(下面详述)。
  左边是表,**点任一行右边就出这块料的详情**:这条需求要多少、发了多少、
  还差多少,以及这颗元件本身的值/封装/料号/现有库存/分布在哪个仓位。
  **品类点「换…」一级一级改** —— 选完大类才出二级,二级下面有三级才出三级,
  没有了就停;改完立刻落库,并刷新明细、收料、出库三处。
  为什么不做成一个装着全路径的长下拉:路径一长,框里只看得见结尾那几个字
  (「… / 陶瓷贴片电容 / 0603」),根本不知道自己在选哪一支,而选错品类的代价
  是这颗料以后按品类找不到。每一级都能「＋ 新建…」,挑到一半发现「钽电容」
  这档还没有就当场加上;推断不出来的品类(光耦、传感器模块…)照旧能直接打字填
- **元件入库 / 元件出库** —— 真正的收料和发料。各是一个开单区 + 这个项目在这个方向的
  记录表(按时间倒序),右上角能直接撤销。
  - 两边**都必须先选项目**:入库/出库都要记在项目名下,否则「这批料是为谁收的」
    就丢了。没选项目时点确认会被挡住并说明原因。
  - 开完单记录表**立刻**多一条,而且开单表上的「现有 / 还差」也会跟着重算。

  每个方向有**两种开单方式**,默认是「按 BOM」:

  | | 按 BOM(**默认**) | 自由 |
  |---|---|---|
  | 入库 | 按 BOM 收料:勾选清单,数量默认取 BOM 需求,**一次全收进来** | 找一颗料、填数量 |
  | 出库 | 按 BOM 出库:每条需求展开能凑它的库存料,**一条需求可以由几颗料凑齐** | 找一颗料、填数量 |

  为什么默认按 BOM:记录本来就挂在项目名下,而项目就该照 BOM 收发货 ——
  「这颗料该不该收、该收几个」的答案本来就在那张 BOM 里。**自由**那条路是留给
  不在 BOM 上的东西的(螺丝、锡、随手补的料),它不该是主路径,但也不能没有。

  #### 按 BOM 收料(`BomReceivePane`)

  一箱货到了,勾掉收到了的,一次全收进来。

  - 一行 = **一条 BOM 需求**(不是一颗库存元件),所以「该收什么」不用自己回忆
  - **单独一列写着品类。** 收料时最容易出错的恰恰是「这个看起来像电阻的东西到底
    是不是电阻」:值和封装都对不上时,品类是最后一道人工检查
  - **数量默认填这条需求还没收的那部分**(`remaining` = 需要 − 已发料 − 已入库),
    不用自己算 —— 让人每行去算「还差几个」是在把库房的账推给记性,而记性会出错。
    已经收了多少后端记着(`received_qty`),再让人拿总需求去减等于明知故问。
    双击一行可以手改,手改过的值在刷新时保留
  - **前面是可勾选的小框**(`☑` / `☐`,先点「选」那一列、或选中按空格),
    勾好的行点一次「✓ 勾选的全部入库」就全部落库
  - **货只到了一部分时,用「✓ 只入库选中这一行」。** 选中一行,工具栏那个按钮上
    会直接写出选的是哪一行,点它就只收这一行 —— 不必先去把别处的勾清干净,
    再点一个**字面写着「全部」**的按钮。右键菜单里也有同一个动作
  - 单个入库和批量入库**走同一条落库路径**(`move_rows`),所以「数量是 0」
    「没选仓位」「还没选项目」这些挡住的条件对两条路一视同仁。只清掉这次真收了的行,
    **别的勾不会被顺手清掉** —— 否则接着收第二行得重新勾一遍
  - 提交前会把「要收哪几行、共几个」念一遍再动手。两行名字撞车时
    (100nF 0603 和 100nF 0805 现在都叫 `100nF`),确认框里**连封装一起写出来**,
    否则人分不清自己收的是哪颗
  - **入库不会动 BOM 的「已发料」。** 货进仓库不等于发给板子了 ——
    把两者混起来的话,东西一进库界面就会说「齐了」,反而发不出去。
    它记的是另一本账「已入库」,收料页那一列就叫这个名字

  #### 按 BOM 出库(`BomPickPane`)

  **库里 0603 有 8 个、0805 有 2 个,而 BOM 要 10 个** —— 这是常态不是例外,
  导出的 BOM 常常连封装都不写全。所以这里不是一张「库存元件」的平表,而是一棵**分配树**:

  ```
  ▼ 100nF 0603  ×10   [还能出 2]      ← 一条 BOM 需求
      ☑ 100nF C0603        库存 8   本次出库 8   还能出库 2
      ☐ 100nF C0805        库存 2   本次出库     还能出库 2
  ```

  - 父行 = 一条 BOM 需求,写着 **×需求 [还能出 N]**(全齐了写「✓ 齐了」);
    展开箭头下面是**库存里能凑它的料**
  - 每颗候选前面有勾选框,后面两列是 **本次出库 / 还能出库** ——
    勾一颗、填个数,**父行和同一行其它候选的「还能出库」立刻跟着减**。
    上面那张图里勾掉 0603 那 8 个之后,0805 那行的「还能出库」会自动变成 2,
    正好提示你「再勾这颗、出 2 个就齐了」
  - 勾选时默认填 `min(这颗的库存, 还能出多少)`,所以多数情况下连数字都不用敲
  - 候选的排序和理由来自「找相似」(见下),**BOM 自己指定的那颗料只要还有库存
    就一定排在最前面**(标成绿色)—— 它才是 BOM 本来要的东西,相似度再高也只是「像」。
    相似匹配找不到它(值不认、封装也不同)时也会补上,否则用户根本选不到自己写的那颗
  - **BOM 里登记过的替代料也会出现**(哪怕值和封装都不一样):用户设替代料就是
    为了「这颗不够时拿那颗顶」,只按相似度会漏掉它
  - 库存里一颗都凑不出的需求**照样列出来**,展开写着「库存里没有能凑它的料,
    得先入库或设替代料」—— 展开是空白的会让人以为界面坏了
  - **「自动配齐」**按相似度从高到低先配一遍,但**只填勾选、绝不自动提交**;
    凑不齐的地方会留着,让人看见「这条还差 3 个,库里真没有」
  - 提交前把「要发哪几行、共几个」念一遍。出库是扣库存,点错了要一条条撤销

  - **收料和发料是两本账**(#31):`project_bom.received_qty` 记「已入库」,
    `placed_qty` 记「已发料」,一行的 `remaining = max(0, need − placed_qty −
    received_qty)` 由 `bom.shortage_report()` 一处算好。只记「已发料」的话,
    「这条需求收到哪一步了」就没地方看,只能靠人拿总需求去减 —— 那正是出错的源头
  - **两个面板只列 `remaining > 0` 的行,而且是接口层就挡掉**
    (`/api/projects/<id>/bom?pending=1`、`project_pick_plan()` 里 `remaining <= 0`
    直接跳过)。这是账的口径,不是某个面板的显示偏好 —— 收料页、出库页、以后新加的
    入口都该是同一个「这条需求还欠着吗」的答案;让每个调用方自己记得筛,迟早漏一个,
    那一行就又冒出来。挡掉几条会回一个 `hidden_done`,界面才说得出
    「N 条已经做完,不再列出」(只看到行数变少,人第一反应是「我的 BOM 呢」)。
    BOM 明细页不带 `pending`,照旧看全貌 —— 在那里藏行才是真丢数据
  - **已发料记在 BOM 需求上,不是记在元件上**(`movement.bom_id`)。一条需求由
    0603 出 8 个、0805 出 2 个凑齐,光看元件号分不清它们是在顶同一条需求。
    撤销其中一笔时,**那条需求的「已发料」会跟着退回去** —— 不退的话界面会说
    「还差 0 个」,而东西其实已经还回架上了。撤销**按方向分别冲**:入库撤销退
    `received_qty`、出库撤销退 `placed_qty`,两边都 `MAX(0, …)`(撤成负数比不冲还难查)
  - 注意区分 **缺口 `gap`** 和 **`remaining`**:前者是「库里还差多少」(发料不会让
    库存回来),后者是「这条需求还要收 / 发多少」。界面上它叫**「还没动」**(收料页)/
    **「还能出库」**(出库页)—— 减掉的是两本账,叫「还需要」会让人以为只扣了发料。
    发完一批之后后者归零、前者照旧

- **导入 BOM:`.xlsx` 和 `.csv` 都行**,`bom.parse_any()` 按扩展名分派,
  但两种格式**共用同一套行解析**(`rows_to_items`)—— 所以识别规则、告警、品类推断
  不会各走各的。CSV 侧额外处理了三件真实存在的事:
  - **编码**:按 `utf-8-sig → utf-8 → gb18030 → gbk → big5` 试。中文 Excel 另存为 CSV
    往往是 GBK,而 KiCad / 立创导出的是带 BOM 的 UTF-8,两个都得认,不能让用户先去转码
  - **分隔符**:按第一行里出现最多的那个猜(`,` / `;` / Tab / `|`)。欧洲区域设置的
    Excel 会用分号,有些工具导出制表符
  - **表头别名**:同时认 Altium(`Designator`/`Comment`/`Quantity`)、
    KiCad(`Reference`/`Value`/`Footprint`/`MPN`/`LCSC`)、
    EasyEDA 与立创(`Comment`/`Manufacturer Part`/`Supplier Part`),以及全中文表头
    (`位号`/`数量`/`值`/`封装`/`厂家料号`)
  - **没有料号的行不再丢弃**。识别走元件自己的**身份键** `component.identity_key`,
    按 商品编号 → 厂家料号 → 值+封装 依次回退 —— KiCad / EasyEDA 的默认导出经常
    只有 Value + Footprint,以前这种行会被整行跳过。**身份键和显示名是两回事**
    (见下),所以改显示规则不会影响「哪两行是同一颗料」
- **导入前会先把品类过一遍**(`BomReviewDialog`)。品类是「按品类找料」「按值筛选」的
  基础,而推断难免出错 —— 导出格式五花八门,缺位号、写错封装、把料号填进值那一列,
  都会让推断跑偏。但**让人从头看一遍是不现实的**,他只会直接点确定,那这步就白加了。
  所以复核窗口的做法是:
  - **默认只列「要确认」的行**(线索打架的、只有弱证据的、认不出的)。判断依据来自
    `bom.classify()` 返回的把握等级:证据来自 BOM 自带的品类列、封装强特征、位号前缀、
    值的单位这四档算「明确」;只靠封装形状这种弱证据算「要确认」;一条线索都没有算
    「认不出」。前两档之外的都要人看一眼
  - **每一行都写着推断依据**,比如「位号 C 开头,按惯例是电容;值 10kΩ 的单位是 Ω,
    Ω 只能是电阻。这几条线索互相矛盾,请人工确认」—— 人扫一眼就知道该不该改
  - **多选之后下拉一选、点「应用」可以一次改掉一片**;双击一行能单独改
  - **那个下拉是建议,不是限制 —— 可以直接打字。** 推断不出来的品类(光耦、
    传感器模块……)必须能自己填,否则用户只能从给定的词里挑一个最接近的凑合,
    那等于把「猜错了」换成了「被迫选了个不准确的」。选项里还并上了**用户自己
    库里已经在用的品类**,他自己用惯的词在这里也选得到
  - 想从头看就把「只看要确认的」关掉
  - 确认后只把**改过的那几行**按行号回传(`{行号: 品类}`),没改的仍用推断结果。
    按**行号**而不是按位置回传,因为解析会跳空行、合并重复行,按位置对会整体错位
- **导入 BOM 的品类是怎么猜的**(`bom.classify()`)。四档证据按优先级投票,优先级高的
  胜出;投出来的结果不一致时**降级成「要确认」并把冲突写进依据**,交给上面那个复核窗口:
  1. BOM 里自带的品类列(`分类`/`类别`/`category` 等)。故意不认 `type` / `kind` ——
     那两列在导出里常常指的是贴片/直插,不是品类
  2. 封装的强特征:接线端子族(`KF301`/`KF128`/`KF2EDG`…)、USB 座、`SOD-`/`DO-214`
     二极管外形、`XTAL`/`CRYSTAL` 晶振、`LED_`/`LED-` 发光二极管。**发光二极管那条必须
     排在弱规则前面** —— LED 封装名里常带 `0805`/`0603`,不挡住就会被认成电感
  3. 位号前缀:`R` 电阻、`C` 电容、`L` 电感、`D` 二极管、`Q` 三极管/MOS、`U` 芯片、
     `J`/`P` 连接器、`Y`/`X` 晶振、`F` 保险丝、`K` 继电器 …
  4. 值的单位:`10kΩ` → 电阻、`100nF` → 电容、`4.7uH` → 电感,`R47`/`4R7` 里的 R 是
     欧姆位也算电阻。这条是给**没有位号**的导出准备的 —— 那种 BOM 里值往往是唯一的线索
  - 单位都没有的裸数值(`10k`)不硬猜;料号形状的值(`CH224K`)不会被当成标称值
- **出库找料:按「值 + 封装」找相似**(`SimilarDialog`)。导出的 BOM 常常缺料号、缺位号,
  只剩值和封装,而且同一样东西不同工具的写法还不一样(`4.7k` / `4.7kΩ` / `4700`;
  `C0805` / `0805` / `C-0805`)。严格相等找不到,人就得自己在几百行里翻。两个入口:
  - BOM 明细工具栏的 **「找相似库存…」** —— 拿选中那一行的值+封装去库存里找
  - 开单区的 **「找相似…」** —— 用当前选中元件(或搜索框里打的字)去找。
    **入库方向刻意不勾「只看有库存的」**:要收的料现在库存本来就是 0
  - 候选按「像到什么程度」排序并**写出理由**:值和单位都相同 +60、数值相同只是写法不同
    +60(但说法不同)、封装相同 +30、封装写法相近 +15、品类相同 +10。分数一样时
    **有库存的排前面**——找相似多半是为了出库,没库存的帮不上忙
  - **给了值却对不上值的一律不算候选**。只对上封装的(比如拿 `4.7k 0603` 去找,
  却列出 `100nF 0603`)在「值」这个主判据上彻底错了,列出来纯属噪音
  - 界面上分三档说法:**「很可能是同一颗」(≥90)/「值对上了,封装要自己看」(≥50)/
    「只是有点像」**。这里**不替人认定是同一颗料** —— 出库记错料,比多花两秒确认严重得多
  - 从 BOM 明细里挑中之后**自动切到「元件出库」,并把「这条需求用这颗料顶」
    挂到分配树上勾好、按缺口填好数量**:找相似的目的十有八九就是这条 BOM 需求
    拿这颗料凑,让他再回一张平表里自己找一遍,等于把他刚做完的判断丢掉。
    挂不上(这颗料不是这条需求的候选,比如它现在根本没库存)就退回「自由出库」
    把它选中;两条路都走不通时**一定弹消息说明** —— 悄悄切个页什么都不做,
    用户只会以为按钮坏了
- 左侧项目列表:**计划**(打算做几块)/ **能造**(照现在的库存最多能装出几块)/
  料号数 / 缺料行 / 状态。**能造几块由最缺的那一行决定**,所以只要看哪一行是红的、
  以及「料号/缺料行」这两个数,就知道卡在哪
- 右侧 BOM 明细 12 列:**名称 / 商品编号 / 值 / 封装 / 单块 / 损耗 / 需求 / 现有 /
  替代 / 缺口 / 标记 / 位号**。「标记」那一列会写 `可选` / `免点` / `替代N`
- **双击一行**就能改单块用量、损耗率、固定损耗,以及标成:
  - **可选件** —— 缺了不影响「能造几块」(上游 InvenTree 是把可选件也算进产能的,
    这里不这么干:一个可以合法省掉的件不该把产能直接归零),缺的另算在 `optional_missing` 里
  - **免点件** —— 螺丝、锡这类,算需求但不卡产能
- **替代料**:给一行挂上可以顶替的料号,替代料的现有库存会算进这一行的可用量
  (`available = 现有 + 替代料现有`),所以「能造几块」也跟着变
- **需求数量**按 InvenTree 的口径算,`BomItem.get_required_quantity` 那一套:
  `需求 = ceil(单块用量 × (1 + 损耗%) × 计划数量) + 固定损耗`
- **缺料转采购**:一键把还差的部分(`to_order`)加进采购单,已经在途的不会再加一遍
- 导出缺料清单 CSV(带 BOM 头,Excel 直接打开不乱码)
- 实时联动:入库之后回到这一页,缺料和能造数量立刻重算

### 5. 采购

一页管住「我要买什么」,上下两块:

- **上面:该买什么**(算出来的)。每行都写了**为什么**,比如「项目缺料 / 低于安全库存」,
  并按 现有 / 安全 / 需求 / 在途 / 该买 / 单价 / 金额 / 供应商 排开。
  触发条件是 `to_order > 0 OR on_order > 0`(在途的也要显示,否则你不知道自己下过单)
- **下面:采购单**(你真正下的单)。状态四种:

  | 状态 | 含义 | 算不算在途 |
  |---|---|---|
  | `todo` | 想买 | **不算** |
  | `ordered` | 已下单 | **算** |
  | `arrived` | 已到货 | 不算(货已经到了,进现有) |
  | `cancel` | 已取消 | 不算 |

- 流程:勾选该买的 →「把选中的加入采购单」→ 真下过单了点「标记为已下单」→
  到货了点「到货入库…」
- **允许分批到货**:入库时数量可以改小,剩下的继续留在在途,全收完自动转 `arrived`
- 到货会写一条带 `purchase_id` 的 **IN 流水**,所以在「流水」页能追到这张单

### 6. 仓位

- 支持 **A柜 / 01层 / 02格 这样的层级**,不再是平铺的一堆名字。
  `location` 表用 `parent_id` 自引用,显示成 `路径` 的样子(如 `A柜 / 01层 / 02格`)
- 建仓位时有个 **「只用来分层」** 的勾(`structural=1`):勾上的节点(「A柜」「01层」)
  本身是**架子**,不装东西。往这种仓位直接入库会被后端拒绝并提示放到子仓位 ——
  否则东西会被记到一个其实没有物理位置的节点上,回头根本找不着
- 删除仓位时:有子仓位、或里面还有库存,都会被拦住
- 选中上层仓位,右边**级联**列出它下面所有仓位里的料(`WITH RECURSIVE`),
  并给出 `含子仓位:N 种 / M 个   估值 X 元`
- **📋 盘点这个仓位…**(实物清点)。实物清点总是「一个抽屉一个抽屉」地做,
  而不是「一个元件一个元件」地做,所以入口在这里而不是在元件页。
  要点是**用键盘走一遍**:输入实数、回车,自动跳到下一个还没数的,全程不用碰鼠标。
  只把**有差异**的行写成 `ADJUST` 流水 —— 对得上的不留痕,否则流水会被几百条
  「没变」淹掉,真出事时反而查不出来。「账面有、实物没数到」也是差异(填 0 即可)。
  只数了一部分也能保存,没数到的保持原样不动(会先问一句)。
  分层仓位本身没有实物可数,会被直接拒绝。

### 7. 流水

所有出入库记录,含时间、动作、数量、仓位、操作人;可按动作类型筛选。
到货入库的记录带采购单号,能一路追回「采购」页。

- **按项目分组**(#30)。这些记录天生是「一个项目一堆」,平铺成一张长表时,
  几十个项目混在一起根本看不出哪几笔是同一件事 —— 所以一个项目一行
  (`项目名(N 笔)`),记录挂在它下面,**默认是收着的**(用户原话:一直展开在那边
  太乱了)。点组行就展开/收起,`▶ / ▼` 直接告诉你现在哪种状态;组里几笔也写在
  组行上,收着也能数。没挂项目的那些(手动补货、领用)单独一组,名字叫
  `(不开项目)`。展开状态在本次运行里记住,刷新、撤销都不会把收好的组又弹开。
- **组行不是一笔账**。撤销要选中下面具体的那一笔;点组行会被明确挡住并提示一句。
  键盘上下键仍然能把选中挪到组行上,所以 `undo()` 里另外还有一道判断 ——
  「正好选中了组行」这种状态下,撤销不能悄悄作用于别的记录。
- 同一套折叠也用在「出入库」页的入库流水 / 出库流水两张表上(同一份代码)。

- **↶ 撤销(Ctrl+Z)**。这套东西的取向是「收货即录入」,好处是数据不会烂,
  代价是**录错反而更容易发生** —— 所以必须留一条退路。按 Ctrl+Z 或者点
  「撤销上一次出入库」,确认一下那一笔是什么,就退回去了。流水页上选中任意一条
  也能单独撤销(包括撤销某一次盘点)。
- 撤销的做法是**补一笔反向流水**,把原记录标成「已撤销」,**不删记录**。
  理由:这套东西的口径是「流水只增不改、余额随时能按流水重建」——
  删一笔就再也重建不出来,而且事后查不出「那天到底是谁把它改成这样的」。
  已撤销的行在流水页淡显但不隐藏,反向流水也照样列在那儿。
- 撤销「采购到货」时,采购单的已收数量会一起退回去(否则那张单永远收不完);
  撤销盘点时,靠流水里的 `qty_before` 回到盘点前的数量 —— 所以旧版本的盘点记录
  没有这个字段,会被明确拒绝而不是猜一个值。
- 反向流水本身也是一笔正常流水,所以**按流水重建余额的逻辑一行都不用改**。

## 元件身份和显示名是两件事

这是踩过的一个坑,记在这里免得以后又合回去。

早期 `build_name()` 把显示名拼成 **`值 + 空格 + 封装`**(`1uF 0805`),
而 `find_component()` 在既没有商品编号、也没有厂家料号时,**就是拿这个名字找同一颗料的** ——
对 KiCad / EasyEDA 那种「只有 Value + Footprint」的导出,那是唯一的识别依据。

于是**名字同时兼任了身份键和显示名**。后果是:只要动了显示规则(比如「100nF 就是
100nF,别带封装」),匹配行为也跟着变 —— `100nF 0603` 和 `100nF 0805` 会算出同一个
名字,下一次导入把两颗**不同的料静默并成一条**,BOM 需求和库存全跟着错,
而且不报错、界面上看不出来。

现在拆成两列:

| | 用途 | 内容 |
|---|---|---|
| `component.identity_key` | 匹配(导入、查重) | `lcsc:C12345` / `mpn:RC0603…` / `vp:100NF\|0603` |
| `component.name` | 只给人看 | 值(`100nF`);值为空才退回料号 / 商品编号 / 品类 |

- **值和封装都要进 `vp:` 那个键。** 少任何一个,`100nF 0603` 和 `100nF 0805` 就会撞车。
  封装先做归一化(去掉空白和 `-` `_` `/` 再大写),所以 `C0805` / `c0805` / `C-0805`
  是同一个键
- **什么都判断不出来时 `identity_key()` 返回空串,而不是某个光秃秃的前缀。**
  返回前缀会让所有「什么都没有」的元件共用一个键、一导入就整批并成一条;
  返回空串则退化成「不匹配」—— 宁可多一条重复,也不要乱并
- **迁移只改能确定是自动生成的名字**(`name` 正好等于 `f"{value} {package}"`),
  用户自己起的名一律不动:猜错的代价是把人家的命名默默抹掉,比名字里多带一个封装难查得多。
  迁移是幂等的。改名字不伤任何关联 —— BOM、流水、单据引用的都是 `component.id`
- 回归自检里专门有一节盯这件事:同一块 BOM 里同时放 `9.09k` 的 `SELFTEST-A` 和
  `SELFTEST-B` 两个封装,**反复导入必须始终是两条**

## 数据模型

```
category      品类树(菜单的骨架)
              parent_id 指向上一级(NULL = 顶层),所以级数不受限
              component.category_id 指向具体节点,component.category 存**顶层祖先
              的名字** —— 全程序里「按品类分组 / 筛选 / 显示」的 SQL 读的都是那个
              文本列,让它继续只认顶层,这些 SQL 一行都不用改;
              代价是两者必须一起写,绝不允许文本和 id 互相矛盾
              顶层重名靠部分索引拦(SQLite 的 UNIQUE 对 NULL 不生效)
component     元件主数据(lcsc_pn 唯一)
              params 是自己定义的属性(耐压 / 精度 / 功率 / 饱和电流…),
              存 JSON,所以加新属性永远不用改表结构
              identity_key 是判断「两次导入的是不是同一颗料」的依据,按
              lcsc: <商品编号> → mpn: <厂家料号> → vp: <值>|<封装> 依次生成。
              **它和 name(显示名)是分开的两件事** —— 名字只放值(100nF),
              封装在自己那一列;匹配绝不看名字,所以显示规则怎么改都不影响识别
              merged_into 指向合并后保留的那条;非空的行不再出现在列表里,
              但流水、单据、BOM 都还查得到它 —— 合并是标记,不是删除
location      仓位
stock         库存余额 = 元件 × 仓位
movement      出入库流水(只增不改)
              voided=1 表示这笔被撤销了;void_of 指向它在撤销哪一笔;
              qty_before 是这一笔之前该仓位的数量(撤销盘点要用)
project       项目
project_bom   项目 BOM = 项目 × 元件 × 需求数量 + 位号
bom_substitute 某一行 BOM 的替代料
purchase      采购单(received 是已收数量,决定还剩多少在途)
```

> 「只增不改」是这套东西的地基:`stock` 随时能用 `movement` 重建出来并校验
> (「工具 → 按流水重建库存余额」)。撤销因此也不能靠删记录 —— 补一笔反向流水
> 就同时满足了「退得掉」和「账本还能重建」。

设计要点:

- **一条流水为哪条 BOM 需求发的**(`movement.bom_id`)。一条 BOM 需求常常由几颗
  不同的库存料凑齐(0603 出 8 个 + 0805 出 2 个),光看 `component_id` 分不清它们
  是在顶同一条需求。项目 BOM 被重新导入时旧行的 id 会消失,这一列就置空 ——
  与其记一个指向别处的号,不如老实说「那条已经不在了」。
- **余额与流水分离**。流水是原始记录,余额是物化结果。设 `POST /api/rebuild` 可按流水顺序重放并重建余额,用来校验两者是否一致(实测差异恒为 0)。
- **仓位相关参数放 JSON**(`component.params`),比如 `{"耐压":"50V","精度":"±1%"}`,避免为每个品类加列。

## 导入 BOM 的要求

支持 Altium / KiCad / EasyEDA / 立创 导出的 **`.xlsx` 和 `.csv`**(也能读 `.tsv` / `.txt`),
列名**不区分大小写、自动识别中英文**,编码和分隔符自动识别。

必需两列(缺了会明确报错):

| 规范字段 | 可接受的表头写法 |
|---|---|
| 位号 | `Designator` / `Reference` / `RefDes` / `位号` / `元件标号` / `元件编号` |
| 数量 | `Quantity` / `Qty` / `数量` / `用量` / `Amount` / `PCS` |

可选列:

| 规范字段 | 可接受的表头写法 |
|---|---|
| 厂家料号 | `Manufacturer Part` / `MPN` / `Part Number` / `厂家料号` / `厂商型号` |
| 厂家 | `Manufacturer` / `Mfr` / `Brand` / `厂家` / `制造商` |
| 商品编号 | `Supplier Part` / `LCSC` / `LCSC Part #` / `供应商料号` / `商品编号` / `商品编号` |
| 供应商 | `Supplier` / `Vendor` / `供应商` |
| 注释 / 值 / 封装 | `Comment` / `Value` / `Footprint` / `Package` / `注释` / `值` / `封装` |

导入时的行为:

- 识别键按 **商品编号 → 厂家料号 → 值+封装** 依次回退。
  第三档是必须的:KiCad / EasyEDA 的默认导出经常只有 Value + Footprint,
  只认前两档的话这种 BOM 一行都导不进来
- 已有元件只**补空字段**,不覆盖你手工改过的值
- 位号数与数量不一致会给出警告,以数量为准
- 位号支持 `C1,C2,C8` / `C1 C2 C8`(KiCad 用空格)/ 中文逗号 / 顿号 / 分号
- 品类按 **封装特征 → 位号前缀** 自动推断(如 `USB1` / `CONN-*` → 连接器,`RES-ADJ` → 电位器)
- 导入时就把 `value_num` / `value_unit` 算出来 —— 否则「刚导完就按阻值排序 / 筛区间」
  会不准(以前要等下次启动的 backfill 才补上)

> 已用你桌面上 `BOM_Board1_PCB1_2026-10-01.xlsx` 实测:20 行读取完整、
> 19 个元件、位号 1~19 齐全、总用量 39、**0 条警告**。
> CSV 侧覆盖了 KiCad 列名、立创列名、全中文表头 + GBK 编码、分号分隔四种情况。

## 常见问题

**双击 exe 没反应 / 弹了个报错框?**
打开 `data\gui.log` 看最后几十行,原因基本都写在里面。日志里若**没有**
「`[就绪] 窗口已显示`」这一行,说明窗口根本没起来,那几行 traceback 就是答案。

**提示"程序已经在运行了"?**
同一时刻只允许开一个窗口(避免两个窗口改同一个数据库)。到任务栏找那个窗口,
或先在任务管理器里结束 `pythonw.exe`。

**关掉窗口后任务管理器里还有 python.exe?**
正常不会。若有,确认不是在跑**旧版网页版**(`app\server.py`)——那一版靠心跳超时退出。

**中文显示成乱码?**
桌面版窗口用系统字体,不涉及编码;启动器给子进程设了 `PYTHONUTF8=1`,
所以 `data\gui.log` 也是 UTF-8。若记事本打开日志像乱码,换 VS Code 打开即可。

**想换台电脑用?**
把 `dist\元器件物料管理\` 整个文件夹拷过去,双击 exe 即可,**目标机什么都不用装**。
exe 必须和 `runtime\`、`app\` 两个文件夹放在一起,单独拷 exe 是跑不起来的。
(从源码跑才需要目标机有 Python 3.10+,且必须带 tkinter。)

**`data/tmp/` 里有个删不掉的空目录?**
那是最初在 DSH 沙箱里试装 Python 包时留下的痕迹(受限进程建的目录带保护性权限项)。与本系统无关,系统不使用该目录,忽略即可。

## 设计说明

### 为什么零第三方依赖?

原计划用 FastAPI + Uvicorn,但实测发现:本机环境下 `pip` 无法工作——
CPython 的 `tempfile.mkdtemp()` 在 Windows 上会创建**不继承父目录权限**的目录,
而 DSH 沙箱的写入许可是靠继承传递的,于是 pip 建临时目录这一步必然被拒。

改用纯标准库后:不需要 pip、不需要虚拟环境装包、不需要任何权限放宽,
而且顺带得到一个能跑在**任何 Python 3.10+** 上的自包含程序。

### `xlsx.py` 为什么自己写?

为了不依赖 `openpyxl`。xlsx 本质是一个 zip 包着若干 XML,
BOM 这种规整表格只需要读共享字符串表和单元格值,约 150 行足够。
已与 `openpyxl` 逐值比对,结果一致(且更干净:不会多出一个全空的尾行)。

## 附:第六轮修掉的几个毛病

这些是实际用下来撞到的,不是想出来的:

**钻取时旧页面没被收走** —— `_swap()` 只收起了首页和列表页,漏了「选子类」那一页。
于是从选子类进到列表页时两页同时铺着、上下各占一块(看起来像"上下分页"),
选子类那一页还活着、卡片还能一直点,面包屑就一段一段往上加
(`全部库存 › 电容 › 贴片陶瓷电容 › C0805 › C0805 › C0805`),「返回」也只是改了路径。
三个症状同一个根因。现在三个页面互斥,连点同一张卡片也不会重复追加。

**有子类的品类,本级挂着的料进不去** —— `_descend()` 只要看到有子类就只给子类卡片,
而「大类下面既有细分的子类、又有还没细分的料」是很常见的摆法(库里的电容正是如此:
4 颗挂在大类上,下面又分了贴片/直插)。现在中间页多一张「本级(挂在这里的)」,
点进去就是这一级自己的料,不含子孙。

**卡片上的「N 种在库」把零库存也算进去了** —— 卡片数的是元件条数,列表按 `stocked=1`
过滤,于是零库存的品类也喊"在库",点进去一行都没有。现在卡片只数**有库存**的,
和点进去看到的完全一致;「品类管理」窗口里那套「直接挂 / 含子类」仍旧数全部元件
(那是整理分类用的),两套口径分开。

**BOM 文件里的「分类」列会把封装/位号的判断盖掉** —— 实测有两颗 `R0603` 的
`0Ω` / `20kΩ` 被文件写成「电容」,于是电阻住进了电容的子树。现在文件写的品类和封装
明显不是一类时以封装为准,并把理由写在复核界面里
(「BOM 里写着「电容」,但封装 R0603 是电阻 —— 以封装为准」);
字符串互相包含(「贴片陶瓷电容」⊃「电容」)算一致,「其他 / 未分类」和认不出的封装都不动。

**顺带修的数据** —— 上面那两颗电阻已经从「电容 / 贴片陶瓷电容」挪回「电阻」,
改前备份在 `build\cache\parts_before_r6_*.db`。

## 附:第十一批修掉和加上的东西

- **品类完全交给用户:卡片只列库里真有的,每一个都删得掉,删了不回来**(#32)。
  用户原话是「品类属于用户的事情,我需要是绝对的自定义自由化」。改完之后的样子见
  上面「2. 库存」「2.3 品类树」两节,这里记实现上值得留下的三个点:

  - **播种时机才是根因**。`db.init_db()` 先查 `sqlite_master` 里 `category` 表在不在,
    再 `executescript(TABLES)` —— 于是 `had_category` 就是「这一次才建出这张表」,
    只有它为假时才 `reconcile_categories(seed=True)` 播一次。**故意不用 `meta` 里的
    标志位**:标志位本身是老库没有的一行数据,升级上来的库读不到它,又会被当成新库
    播一遍,正好把病复现;`CREATE TABLE IF NOT EXISTS` 的建表时机是 SQLite 自己维护的,
    不会骗人。`reconcile_categories()` 的 `seed` 默认 `False`,别的调用点(删品类后的
    收尾、合并元件后的对账)都不播种,否则刚删掉的那一行立刻被 `INSERT` 回来。
    「库里已经在用的品类文本」那一步留着 —— 它建的行来自 `component.category` 的真实
    数据,不是标准名单。
  - **删顶层的落点**。`delete_category` 以前把直接挂着的元件兜进「未分类」,而
    「未分类」是后端 `ensure_category` 自动建出来的固定词 —— 删一次长一次,顶层大类
    永远删不干净。现在顶层没有上一级就不给它编一个:元件 `category_id` 置 NULL、
    `category` 文本清空(返回体 `to` 是空串,界面据此说「N 颗料现在没有品类了」,
    不再说「挪到「未分类」」);子类各自升为顶层,并 `_retag_category_subtree()`
    把子树里元件的文本改成自己(不然文本还写着那个已经不存在的大类)。**兜底也不能
    写「未分类」** —— 那个词会通过上面那一步重新长成一个真品类行。
  - **「未分类」是算出来的**:`_is_uncat()` 认两种料 —— `category_id` 为空、或挂在
    某个真叫「未分类」的顶层行下面(老数据的形态,那一行会被当成普通品类,一样删得掉)。
    首页按「整库还有没有这种料」决定摆不摆那张卡片(数全部元件,含零库存的,不然卡片
    会随库存变化忽隐忽现),一件都没有它就不存在,所以它也「删得干净」。
  - 顺带修掉一个一直没露出来的 bug:`_retag_category_subtree` 头上也贴着一行一模一样的
    `DELETE /api/categories/(\d+)` 装饰器,而派发是「取第一条匹配」—— 网页 / HTTP 版调
    `DELETE /api/categories/<id>` 永远 500(少一个参数)。桌面版不走路由表,所以没中。
    `build/checks/check_routes.py` 的输出从 55 条变成 54 条,就是这条重复注册被拿掉了。

- **BOM 两本账:已入库(收料)和已发料(出库)分开记**(#31)。细节见上面「4. 项目 BOM」,
  这里只留一句为什么:**一条需求「收到哪一步了」必须在库里有个数**,不能靠人拿总需求
  去减。`remaining = max(0, need − placed_qty − received_qty)` 只由

## 附:第十二批修掉和加上的东西

- **库存状态的「缺料」改成只看安全库存**(#38)。以前那一档是这样来的:

  ```sql
  WHEN 库存 = 0          THEN 'out'    -- 缺货
  WHEN 库存 < 安全库存    THEN 'low'    -- 偏低
  WHEN 库存 < BOM 需求量  THEN 'short'  -- 缺料   ← 病根
  ```

  最后那条拿**项目 BOM 的需求量**当缺料判据:库里的料明明够、安全库存也没设,只因为某个项目
  BOM 要得比手上多,状态列就写「缺料」。同一个文件里其实早有一句注释写着「需求 / 缺口 / 在途 /
  该买是**项目 BOM 的缺料口径**,摆在库存页只会让人以为『我缺料了』」—— **注释和实现对不上**,
  用户就是被这个坑到的:他库里 19 颗料,`required > on_hand` 的有 16 颗,而库存全 ≥ 1、
  安全库存一颗都没设。

  现在只剩三档,而且**「缺料」就是「到安全库存了」**:

  ```sql
  WHEN 库存 = 0          THEN 'out'   -- 缺货
  WHEN 库存 <= 安全库存   THEN 'low'   -- 缺料(含相等)
  ELSE 'ok'                           -- 充足
  ```

  - 与用户原话一致:「只有当库存状态小于等于安全状态才会标记缺料」。
  - **`out` 必须先判**:`min_stock` 是 `NOT NULL DEFAULT 0`(「没设」就等于 0),要是把 `out`
    并进 `low`,「库存 = 0 且没设安全库存」就会变成「缺料」,正好和用户担心的情况相反。
  - **采购页照旧不受影响**:「该买多少」还是按需求量算(`target` / `to_order`)。库存状态说的是
    "我手上够不够安全线",采购说的是"为了项目我还得买多少",两件事,别顺手"统一"。
  - 同一口径的另外三处(`?state=` 白名单、采购建议里的理由、总览的 `low_kinds`)一并改成 `<=`;
    `STATE_LABEL` 从四档变三档(**「偏低」这个词整个退场**),界面状态栏、网页版、说明书和本文件
    的旧说法全部对齐。
  - 值得记住的一点:**旧口径没有任何一条自检钉着**(全仓库 grep `short` 零命中),删掉它自检会
    照样全绿,但老数据的行为已经变了。所以这一批补了【42】:一条「库存 == 安全库存 → 缺料」的
    边界断言、一条「需求 999、库存 10 → 仍然充足」的回归钉子,并用两次反证(把 `<=` 改回 `<`、
    把旧口径装回去)证明它们真的会红。
